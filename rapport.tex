\begin{abstract}
We present a coverage-guided fuzzing campaign against \texttt{libsixel}~\cite{libsixel},
a C library that encodes and decodes SIXEL bitmap graphics. Using AFL++~\cite{aflpp}
with AddressSanitizer, we fuzz multiple functions and compare results with a
QEMU-mode black-box run on an uninstrumented binary. Our image-loading harness
discovers a \texttt{bad-free} in \texttt{load\_png} reducible to an 8-byte PoC,
matching upstream issue~\#177. All harnesses, seed corpora, and
analysis scripts are publicly available~\cite{ourimpl}.
\end{abstract}

%-------------------------------------------------------------------------------
\section{Q1 --- Harness Design}
%-------------------------------------------------------------------------------

\subsection{Entry Points}
We grepped \texttt{SIXELAPI}-tagged symbols in the installed header and kept only
functions whose signatures accept raw buffers, file paths, or length parameters
--- the indicators of externally-controlled data. We selected three entry points.
\texttt{sixel\_decode\_raw()} is the lowest-level decoder: every higher-level
path (\texttt{sixel\_decode}, \texttt{sixel\_decoder\_decode}, \texttt{sixel2png})
bottoms out here, making it the single point through which all attacker bytes
flow. \texttt{sixel\_decode()} was kept as a second decoder target since it
exercises the callback-setup layer that \texttt{sixel\_decode\_raw} skips.
\texttt{sixel\_encoder\_encode()} was chosen for the image-loading path: it
dispatches to libpng, libjpeg, and the BMP loader, exposing far more branching
than any pure decoder --- and it was the only entry point that produced crashes.
Rejected candidates: \texttt{sixel\_encode}, \texttt{sixel\_dither\_initialize},
\texttt{sixel\_helper\_scale\_image} (narrow arithmetic entry points, corpora
saturate below 250 entries), and \texttt{sixel\_decoder\_decode} (I/O-indirection
over the same core parser).

\subsection{Data Flow and Guards}
All harnesses share one skeleton: open the AFL++ input from \texttt{argv[1]},
read it into a heap buffer, validate, call the API, free all allocations.
\textbf{Sixel-stream harnesses} (\texttt{harness\_decode\_raw},
\texttt{harness\_decode}) pass the raw bytes directly to the library; output
buffers allocated by libsixel (\texttt{pixels}, \texttt{palette}) are freed per
iteration to stay compatible with persistent mode. \textbf{File-path harness}
(\texttt{harness\_load\_image}) passes \texttt{argv[1]} to
\texttt{sixel\_encoder\_encode}, which opens the file internally and dispatches
to the appropriate loader; stdout is redirected to \texttt{/dev/null} so SIXEL
escape sequences do not pollute timing.

\textbf{Guard explanations.}
\textbf{(a)}~\texttt{if (argc < 2) return 1} --- protects against manual
invocation during development, which would otherwise crash the harness itself
and produce misleading reports. \textbf{(b)}~\texttt{if (!f) return 1} ---
prevents NULL dereference in the subsequent \texttt{fseek} when AFL++'s
initialisation probe fails to open a file.
\textbf{(c)}~\texttt{if (size == 0 || size > 1000000)} --- an empty file gives
no coverage signal; the 1\,MB cap prevents raster-attribute headers like
\texttt{"100000;100000q"} from triggering multi-gigabyte allocations that turn
into timeouts/OOM rather than crash signals. \textbf{(d)}~\texttt{if (!data)
return 1} --- a \texttt{malloc} failure under ASan's shadow pressure would be
saved as a false-positive crash; we exit cleanly. \textbf{(e)}~\texttt{free(data);
free(pixels)} --- \texttt{sixel\_decode\_raw} transfers ownership of output
buffers to the caller; fork mode would leak per-process but the OS reclaims on
exit, whereas persistent mode running thousands of iterations would OOM.

\section{Q2 --- Instrumentation and Sanitizers}
%-------------------------------------------------------------------------------

The full build-flag table is in Appendix~\ref{app:builds}
(Table~\ref{tab:builds}). In summary: \textbf{Build~1 (white-box)} uses
\texttt{afl-clang-lto} for collision-free edge IDs plus
\texttt{-fsanitize=address} to catch silent heap corruption, compiled static
(\texttt{--disable-shared}) so AFL's shm map reaches inside the library.
\textbf{Build~2 (black-box)} is plain Clang with \texttt{-g -O1} and no
sanitizer/AFL pass so it can run under \texttt{afl-fuzz -Q}. Both use
\texttt{--disable-python} to work around a \texttt{make install} failure on
Python~3.12+ (removed \texttt{imp} module).

\textbf{Patches: none.} The Dockerfile clones upstream, checks out tag
\texttt{v1.8.6}, and builds with an unmodified \texttt{./configure \&\& make}
--- no \texttt{patch}, \texttt{sed~-i}, or \texttt{git apply}. Every crash is
therefore a real bug against upstream, not a harness-side artefact.

\section{Q3 --- Seed Corpus and Dictionary}
%-------------------------------------------------------------------------------

\textbf{Seeds.} Two hand-crafted SIXEL files (162\,B total) generated by
\texttt{seeds/gen\_seeds.py}. \texttt{epfl.six} (134\,B) renders the EPFL logo
using two palette entries and exercises every major control code: run-length
(\texttt{!N}), carriage-return (\texttt{\$}), newline (\texttt{-}).
\texttt{minimal.six} (28\,B) is the smallest syntactically valid stream
(\texttt{ESC Pq}\,\ldots\,\texttt{ESC\,\textbackslash}), used for harness
sanity-checking.

\textbf{Dictionary.} Nine tokens in \texttt{sixel.dict}
(Appendix~\ref{app:dict}, Listing~\ref{lst:dict}). Formally these are the
\emph{terminal symbols} of the SIXEL context-free grammar: the start symbol is
a DCS string and the body is a sequence of colour, raster-attribute and
sixel-band productions delimited by one-byte terminals. Discovering the DCS
introducer \texttt{ESC Pq} by random mutation has probability $\approx 2^{-16}$
per byte pair; the dictionary hands AFL++ these terminals directly so
\emph{havoc} can splice valid token boundaries from cycle~1.

\textbf{Coverage contribution} (from the 40\,min \texttt{harness\_decode\_raw}
status screen: \texttt{corpus\_count=859}, \texttt{corpus\_found=856},
\texttt{edges\_found=469/1\,065}, \texttt{bitmap\_cvg=44.04\%}):
\emph{Havoc} produced 839/856 new entries (87 with new edges) --- it dominates
because dictionary tokens give havoc material to splice into plausible
positions. \emph{Deterministic} passes produced 16 entries (8 with new
coverage), quickly exhausted on two small seeds. \emph{Splice} contributed 0:
it requires $\geq 2$ corpus entries to combine, and with only two seeds at
startup it never fired.

\section{Q4 --- Campaign Analysis}
%-------------------------------------------------------------------------------

We focus on the image-loading campaign that found crashes
(\texttt{harness\_load\_image}) and the QEMU black-box campaign
(\texttt{harness\_vanilla}); both ran 40\,min on a single core. Status screens
and edge plots: Appendix~\ref{app:plots}.

\textbf{\texttt{harness\_load\_image} (crashes found).} Stability 100\%. Corpus 1\,318 inputs (1\,314 found by mutation), the largest
campaign since PNG/JPEG/BMP parsing exposes far more branches than the pure
decoder; map density 12.66\% (2\,114/16\,697), the large denominator including
libpng, libjpeg and BMP, cycles done 0 (859 pending, 44 pending-favoured ---
corpus still actively growing); 2 saved crashes, 8 hangs.
\emph{Edges curve:} immediate sustained discovery --- 977 edges at $t=60$\,s,
1\,065 at $t=156$\,s, 1\,221 at $t=376$\,s, 1\,384 at $t=580$\,s, 2\,114 at
$t=2\,400$\,s, no plateau. Crashes appeared in the very first recorded
interval (bug triggered within the first minute). \textbf{Did not saturate}:
edge count still rising, 0 cycles completed, pending-favoured entries remained.

\textbf{QEMU (\texttt{harness\_vanilla}).} Stability 100\%; corpus 700
inputs (697 found); map density 0.71\% (463/65\,536) --- the low density is an
artefact of QEMU's fixed 65\,536-slot bitmap, not fewer edges: the raw count
463 matches the instrumented decoder's 469, confirming QEMU explored the same
code; cycles done 3 (21 entries pending); 0 saved crashes.
\emph{Edges curve:} 420 at $t=60$\,s, 463 by $t=307$\,s ($\approx 5$\,min),
flat for the remaining 35\,min. \textbf{Saturated by minute 5}: three completed
cycles, flat curve. Without ASan the fuzzer cannot distinguish silent memory
corruption from normal exits, so it stops finding new paths once the
structural variation space is exhausted.

\section{Q5 --- Crash Triage}
%-------------------------------------------------------------------------------

The \texttt{harness\_load\_image} campaign produced \textbf{2 unique crashes}
(\texttt{id:000000}, \texttt{id:000001}; signal~6/SIGABRT) plus 8 hangs; both
reduce to the same bug (identical ASan trace). \texttt{harness\_decode\_raw}
found none.

\textbf{Reproduce.} Running the harness on the crash yields an ASan
\texttt{bad-free} (full trace in Appendix~\ref{app:crash},
Listing~\ref{lst:asan}). Allocation in \texttt{sixel\_frame\_new}
(\texttt{frame.c:61}); bogus free at \texttt{loader.c:633}.

\textbf{Minimize.} \texttt{afl-tmin} reduced the 60-byte crash to 8 bytes
(86.67\%, 66 executions). The minimized PoC is exactly the PNG magic bytes
(\texttt{89 50 4e 47 0d 0a 1a 0a}) with no IHDR --- the shortest input that
makes libpng fail and trigger the \texttt{longjmp} path leading to the bad free.

\textbf{Root cause.} \texttt{load\_png()} declares \texttt{unsigned char **rows}
at line 315 \emph{without} \texttt{volatile} and initialises it to \texttt{NULL}
at line 332 --- \emph{after} the first \texttt{setjmp} (line 323). When libpng
detects a malformed PNG (here: missing IHDR) its error callback executes
\texttt{longjmp(png\_jmpbuf(png\_ptr), 1)}, jumping back to the second
\texttt{setjmp} at line 345. Per C11~\S7.13.2.1, a non-\texttt{volatile} local
written between \texttt{setjmp} and \texttt{longjmp} has \emph{indeterminate}
value after the jump; the compiler may keep \texttt{rows} in a register that
\texttt{longjmp} restores to a stale value. Execution falls through to the
\texttt{cleanup} label, which calls \texttt{sixel\_allocator\_free(allocator,
rows)} on that garbage pointer.

\textbf{Classification.} ASan \texttt{bad-free}; CVE-2020-11721; CWE-825 (Expired Pointer
Dereference --- indeterminate pointer after \texttt{longjmp}) with secondary
CWE-755; matches the root cause of libsixel issue~\#177~\cite{issue177}
(\texttt{heap-buffer-overflow} in the related PNG cleanup path, v1.8.6).

\section{Q6 --- Attack Surface Analysis}
%-------------------------------------------------------------------------------

\textbf{Real-world applications.} \emph{\texttt{img2sixel}} (shipped with
libsixel) converts PNG/JPEG/BMP images to SIXEL for terminal display: any user
passing an untrusted image triggers the full image-loading and decoding
pipeline in their security context. \emph{FFmpeg-SIXEL} streams multimedia
(e.g.\ YouTube) directly to the terminal; because FFmpeg fetches and decodes
remote media, an attacker controlling a media stream can deliver a crafted PNG
that triggers the \texttt{bad-free} with no local file access required.

\textbf{Attack scenario.} The \texttt{bad-free} can lead to arbitrary code
execution in an unsecured remote environment. An attacker crafts an image
forcing \texttt{libsixel} to allocate memory in a predictable pattern; when
the bad free fires, allocator metadata can be corrupted to write
attacker-controlled data into an arbitrary location such as a GOT entry. The
next indirect call redirects execution to shellcode. No authentication or
interaction beyond image delivery is required.

\textbf{Gaps in coverage.} \emph{Gap~1:} \texttt{sixel\_encode()}
(\texttt{src/tosixel.c}) --- the raw encoder processes dimensions and
colour-reduction parameters partially controlled by image metadata; integer
overflow in dimension arithmetic could produce an undersized output buffer.
\emph{Gap~2:} \texttt{sixel\_helper\_normalize\_pixelformat()}
(\texttt{src/pixelformat.c}) performs arithmetic on width, height and
bytes-per-pixel derived from a decoded image. Integer overflow here could
produce an undersized destination, leading to an OOB write our harness never
reaches since we do not call the normaliser after decoding.

%-------------------------------------------------------------------------------
\section{Q7 --- Binary-Only Fuzzing with QEMU Mode}
%-------------------------------------------------------------------------------

The vanilla binary was built with plain Clang (no instrumentation, no ASan)
against a separately compiled \texttt{libsixel-vanilla} and launched under
QEMU. Both campaigns targeted \texttt{sixel\_decode\_raw} for 40\,min.
Side-by-side comparison in Appendix~\ref{app:tables} (Table~\ref{tab:qemu}).

\textbf{Exec speed.} QEMU 409\,exec/s vs.\ instrumented 355\,exec/s
(15\% QEMU advantage). Counterintuitive, but explained by workload: QEMU's JIT
adds first-encounter translation cost, but translated blocks are cached for
every subsequent iteration of the short \texttt{sixel\_decode\_raw} function.
ASan, by contrast, inserts a shadow-memory check before \emph{every} load/store
and runs heap quarantine on every alloc/free, dominating per-exec cost.
Without ASan, compile-time instrumentation would be faster than QEMU; ASan
inverts the ordering.

\textbf{Edges.} 469 (instrumented) vs.\ 463 (QEMU) --- nearly identical. The
gap reflects probabilistic hash collisions in QEMU's fixed 65\,536-slot
bitmap: two distinct edges hashing to the same slot are counted once. The
instrumented build assigns a unique compile-time ID to every CFG edge.
Map-density figures (44\% vs.\ 0.71\%) are not comparable: the instrumented
denominator is the real edge count (1\,065) while QEMU's is its fixed map size.

\textbf{Corpus.} 859 (instrumented) vs.\ 700 (QEMU). Collision-free edge IDs
give a more precise novelty signal: two inputs differing only in which of two
colliding edges they hit are distinct in the instrumented build but identical
to QEMU, so the instrumented fuzzer saves more queue entries and explores
broader mutations.

%-------------------------------------------------------------------------------
\section{Q8 --- Instrumentation Depth and Performance}
%-------------------------------------------------------------------------------

\textbf{Edge counts} (from \texttt{total\_edges} at startup):
\texttt{harness\_decode\_raw} \textbf{1\,065 edges} --- only what is reachable
from \texttt{sixel\_decode\_raw} after linker dead-code elimination (encoder,
scaler, pixel-format routines stripped). \texttt{harness\_decode}
\textbf{1\,057} --- nearly identical, confirming both exercise the same decoder
call graph. \texttt{harness\_load\_image} \textbf{16\,697} --- much larger
because \texttt{sixel\_encoder\_encode} pulls in libpng, libjpeg, the
colour-reduction path and I/O wrappers. The 1\,065 vs.\ 16\,697 gap shows how
entry-point selection determines instrumentation scope: the same library
produces very different coverage maps depending on which subsystem the harness
calls.

\textbf{Map density vs.\ total edges.} Density is
$d = e_{\text{reached}}/e_{\text{total}}$. Not all instrumented edges are
reachable from \texttt{sixel\_decode\_raw}: encoder paths, pixel-format
converters and write-side I/O are compiled in (with \texttt{--whole-archive})
but never called. Even among reachable edges, paths gated on rare valid
sequences may need many mutations to discover within 40\,min.

\textbf{Three configurations} (Appendix~\ref{app:tables}, Table~\ref{tab:perf}):
no-sanitizer fork 542\,exec/s, ASan fork 355, ASan persistent 23\,717.
\emph{No-san $\to$ ASan fork ($\approx 35$\% slowdown):} ASan inserts a
shadow-memory check before every load/store and maintains a 1/8-address-space
shadow map; per-op overhead plus higher memory footprint make each fork more
expensive. \emph{Fork $\to$ persistent ($\approx 67\times$ speedup):} fork mode
pays \texttt{fork(2)} and CoW page-table copy on every case; persistent mode
loops inside \texttt{\_\_AFL\_LOOP(1000)}, amortising fork cost over 1\,000
iterations.
