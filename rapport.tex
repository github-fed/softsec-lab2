\begin{abstract}
%-------------------------------------------------------------------------------
We present a coverage-guided fuzzing campaign against \texttt{libsixel}~\cite{libsixel},
an open-source C library that encodes and decodes SIXEL bitmap graphics for terminal
image display.
Using AFL++~\cite{aflpp} with AddressSanitizer instrumentation, we fuzz the
\texttt{sixel\_decode\_raw} decoder entry point and compare results with a QEMU-mode
black-box campaign on an uninstrumented binary.

\end{abstract}

\section{Q1 — Harness Design}
\label{sec:q1}
%-------------------------------------------------------------------------------

\subsection{Entry Points and Motivation}

We explored the public API by grepping \texttt{SIXELAPI}-tagged symbols in the installed
header and filtering for functions whose signatures accept raw buffers, file paths, or
length parameters — the indicators that a function processes externally-controlled data.
Functions taking only integer flags or opaque internal structs were excluded.

We selected three entry points covering the two main subsystems of the library.
\texttt{sixel\_decode\_raw()} is the lowest-level decoder: every higher-level path
(\texttt{sixel\_decode}, \texttt{sixel\_decoder\_decode}, \texttt{sixel2png}) bottoms
out here, making it the single point through which all attacker-controlled bytes flow.
\texttt{sixel\_decode()} was kept as a second decoder target because it exercises the
callback-setup layer that \texttt{sixel\_decode\_raw} skips.
\texttt{sixel\_encoder\_encode()} was chosen for the image-loading path: it dispatches
to libpng, libjpeg, and the BMP loader, exposing far more branching than any pure
decoder harness — and it was the only entry point that produced crashes.
Remaining candidates (\texttt{sixel\_encode}, \texttt{sixel\_dither\_initialize},
\texttt{sixel\_helper\_scale\_image}) were rejected as narrow arithmetic entry points
whose corpora saturate below 250 entries; \texttt{sixel\_decoder\_decode} was rejected
for adding I/O-indirection objects over the same core parser.

\subsection{Data Flow and Guards}

All harnesses share the same skeleton: open the AFL++ input file supplied as
\texttt{argv[1]}, read it into a heap buffer, validate it, call the library function,
then free all allocations.
The two harness families differ in what ``validate'' and ``call'' mean.

\textbf{Family 1 — Sixel-stream harnesses (\texttt{harness\_decode\_raw},
\texttt{harness\_decode}).}
AFL++ supplies a file path via \texttt{argv[1]}; the harness opens the file, reads its
entire content into a heap buffer, and passes the raw bytes directly to the library
API call.
Output buffers (\texttt{pixels}, \texttt{palette}) allocated by the library are freed
after each iteration to keep the harness compatible with persistent mode.

\textbf{Family 2 — File-path harness (\texttt{harness\_load\_image}).}
\texttt{sixel\_encoder\_encode} takes a file path, opens it internally, and dispatches
to libpng, libjpeg, or the BMP loader.
The harness passes \texttt{argv[1]} directly; AFL++ writes the test image file to that
path.
Stdout is redirected to \texttt{/dev/null} to prevent SIXEL escape sequences from
reaching the terminal and corrupting timing measurements.

\bigskip
\textbf{Guard explanations.}

\textbf{(a) \texttt{if (argc < 2) return 1}.}
AFL++ always supplies the input path as \texttt{argv[1]} via \texttt{@@}.
Without this guard a manual invocation during development would crash the harness
itself, not the library, producing a misleading crash report.

\textbf{(b) \texttt{if (!f) return 1}.}
Prevents a NULL dereference in the subsequent \texttt{fseek} call if the file cannot
be opened (e.g.\ on AFL++'s initialisation probe).

\textbf{(c) \texttt{if (size == 0 || size > 1000000)}.}
An empty file would pass a zero-length buffer to the parser, producing no useful
coverage signal and wasting an iteration.
The upper bound (1\,MB) prevents the fuzzer from constructing a raster-attribute header
such as \texttt{"100000;100000q"} that causes the library to attempt a multi-gigabyte
pixel-buffer allocation — which produces a timeout or OOM rather than a
crash signal, starving the fuzzer of feedback.

\textbf{(d) \texttt{if (!data) return 1}.}
A \texttt{malloc} failure under ASan's shadow-memory pressure would produce a harness
crash unrelated to the library; we exit cleanly so AFL++ does not save it as a
false-positive crash.

\textbf{(e) \texttt{free(data); free(pixels)}.}
\texttt{sixel\_decode\_raw} allocates the output pixel and palette buffers and transfers
ownership to the caller.
In fork mode, failing to free leaks memory per process but the OS reclaims it on exit;
we still free to keep the harness suitable for persistent mode, where the same process
runs thousands of iterations and an accumulated leak would cause OOM termination.

\subsection{Build 1 — Instrumented (White-Box, AFL++ + ASan)}

\begin{center}
\begin{tabular}{p{2.4cm}p{4.8cm}}
\hline
\textbf{Flag} & \textbf{Effect / if omitted} \\
\hline
\texttt{CC=afl-clang-lto} & AFL++ LTO instrumentation: collision-free edge IDs in every basic block. Without it, no coverage feedback; AFL degenerates to blind random fuzzing. \\

\texttt{--disable-shared} & Static \texttt{libsixel.a}. A \texttt{.so} loaded dynamically bypasses AFL's shm map giving 0\% coverage inside the library. \\
\texttt{--disable-python} & Skips Python binding installation. Without it, \texttt{make install} crashes on Python\,3.12+ because the \texttt{imp} module was removed; the build fails before the library is installed. \\

\subsection{Patches}

None.
The Dockerfile clones the official upstream, checks out tag \texttt{v1.8.6}, and builds
with an unmodified \texttt{./configure \&\& make} — no \texttt{patch}, \texttt{sed~-i},
or \texttt{git apply}.
Every crash is therefore a real bug against upstream, not an artefact of harness-side
weakening.

\section{Q3 — Seed Corpus and Dictionary}
\label{sec:q3}
%-------------------------------------------------------------------------------

\subsection{Seeds}

Our seed corpus contains two hand-crafted SIXEL files (generated by
\texttt{seeds/gen\_seeds.py}) totalling 162 bytes:

\begin{description}
  \item[\texttt{epfl.six} (134\,B)] Renders the EPFL logo using two palette entries,
    run-length encoding (\texttt{!N}), carriage-return (\texttt{\$}), and
    newline (\texttt{-}) — exercises every major SIXEL control code.
  \item[\texttt{minimal.six} (28\,B)] A single-color $1\times6$ image: the smallest
    syntactically valid SIXEL stream (\texttt{ESC Pq} … \texttt{ESC \textbackslash}),
    used to verify harness correctness and give the fuzzer a minimal starting point.
\end{description}

\subsection{Dictionary}

The project-local dictionary \texttt{sixel.dict} contains the following token entries:

\begin{lstlisting}
header_pq="\x1bPq"      # DCS introducer + 'q' (most common form)
header_p="\x1bP"        # DCS introducer without mode byte
terminator="\x1b\\"     # String Terminator (ST)
color_intro="#"          # palette entry / color selector
raster_attr="\""         # raster-attributes introducer
rle_intro="!"            # run-length encoding introducer
graphics_cr="$"          # graphics carriage return
graphics_nl="-"          # graphics newline (advance one sixel band)
param_sep=";"            # parameter separator
\end{lstlisting}

In formal terms, these entries are the \emph{terminal symbols} of the SIXEL
context-free grammar.  The grammar's start symbol is a DCS string
(\texttt{ESC P} \ldots{} \texttt{ESC \textbackslash}); the body is a sequence of
color-introduction productions, raster-attribute productions, and sixel-band
productions, each delimited by the single-character terminals above.
Without the dictionary, discovering the two-byte DCS introducer \texttt{ESC Pq}
by random mutation has probability $\approx 2^{-16}$ per byte pair; the dictionary
hands AFL++ these terminals directly, letting \emph{havoc} splice valid token
boundaries into otherwise-garbage inputs from the first cycle.

\subsection{Coverage Contribution}

From the AFL++ status screen after the 40-minute \texttt{harness\_decode\_raw} campaign
(\texttt{corpus\_count: 859}, \texttt{corpus\_found: 856}, \texttt{edges\_found: 469}
of 1\,065 total; \texttt{bitmap\_cvg: 44.04\%}):

\begin{itemize}
  \item \textbf{Havoc} produced \textbf{839} of the 856 new corpus entries,
    of which \textbf{87} triggered genuinely new edge coverage (\texttt{+cov}).
    This stage dominates because the dictionary tokens give havoc material to
    splice into structurally plausible positions, rapidly reaching palette and
    run-length code paths.
  \item \textbf{Deterministic} passes (\texttt{op:(null)}) produced \textbf{16}
    entries, \textbf{8} with new coverage — useful early on for simple byte-flip
    and arithmetic discoveries but quickly exhausted on the two small seeds.
  \item \textbf{Splice} contributed \textbf{0} entries.  Splice requires at least
    two corpus entries to combine; with only two seeds available at startup, and the
    queue growing only through havoc, splice never fired during this campaign.
\end{itemize}

\section{Q4 — Campaign Analysis}
\label{sec:q4}
%-------------------------------------------------------------------------------

We focus on the two campaigns most relevant to Q4: the image-loading campaign that
produced crashes (\texttt{harness\_load\_image}) and the QEMU black-box campaign
(\texttt{harness\_vanilla}).  Both ran for 40 minutes (2\,400\,s) on a single core.

\subsection{\texttt{harness\_load\_image} — Instrumented, Crashes Found}

Key metrics from the AFL++ status screen (Figure~\ref{fig:afl-status}):

\begin{description}
  \item[Stability] \textbf{100\%} — the image-loading chain is fully deterministic.
  \item[Corpus count] \textbf{1\,318} inputs (1\,314 found by mutation), the largest
    of all campaigns; the PNG/JPEG/BMP parsing chains expose far more branches than
    the pure decoder.
  \item[Map density] \textbf{12.66\%} — 2\,114 edges out of 16\,697 instrumented.
    The large denominator includes libpng, libjpeg, and BMP code; many paths require
    specific magic bytes the fuzzer had not yet synthesised within 40 minutes.
  \item[Cycles done] \textbf{0} — the fuzzer never completed a full queue pass
    (859 entries still pending, 44 pending-favoured), confirming the corpus was
    still actively growing at campaign end.
  \item[Saved crashes / hangs] \textbf{2 crashes, 8 hangs}.
\end{description}

\textbf{Edges curve} (Figure~\ref{fig:edges}).
Edge discovery was immediate and sustained: 977 edges at $t = 60$\,s, rising to
1\,065 by $t = 156$\,s ($\approx$2.5\,min), then continuing steadily to 1\,221 at
$t = 376$\,s, 1\,384 at $t = 580$\,s, and 2\,114 at $t = 2\,400$\,s with no
plateau.  Crashes appeared at the very first recorded interval ($t = 60$\,s, 2 saved
crashes), meaning the bug was triggered within the first minute.

\textbf{Saturation.}
This campaign did \emph{not} saturate: edge count was still rising at campaign end,
0 cycles completed, and 44 pending-favoured entries remained.
Longer runtime would continue to uncover new paths.

\subsection{QEMU Mode — \texttt{harness\_vanilla}}

Key metrics (Figure~\ref{fig:afl-status-qemu}):

\begin{description}
  \item[Stability] \textbf{100\%}.
  \item[Corpus count] \textbf{700} inputs (697 found).
  \item[Map density] \textbf{0.71\%} — 463 slots out of a fixed 65\,536-slot
    hash map.  The low density is an artefact of the large fixed bitmap, not fewer
    edges covered; the raw edge count (463) matches the instrumented decoder campaign
    (469), confirming QEMU explored the same code.
  \item[Cycles done] \textbf{3} — three full passes, only 21 entries still pending.
  \item[Saved crashes] \textbf{0}.
\end{description}

\textbf{Edges curve} (Figure~\ref{fig:edges-qemu}).
420 edges at $t = 60$\,s, reaching 463 by $t = 307$\,s ($\approx$5\,min), then
flat for the remaining 35 minutes.

\textbf{Saturation.}
QEMU saturated by minute 5: three completed cycles, 21 pending entries, and a
perfectly flat edge curve for the final 35 minutes.  Without ASan there is no
memory-error signal, so the fuzzer cannot distinguish crashes from normal exits and
stops finding new paths once the structural variation space is exhausted.

\section{Q5 — Crash Triage}
\label{sec:q5}
%-------------------------------------------------------------------------------

\subsection{Crash Found}

The \texttt{harness\_load\_image} campaign produced \textbf{2 unique crash files}
(\texttt{id:000000} and \texttt{id:000001}, signal 6 / SIGABRT) plus 8 hangs.
Both crashes reduce to the same bug (identical ASan call stack).
The \texttt{harness\_decode\_raw} campaign found no crashes.

\subsection{Step 1 — Reproduce}

\begin{lstlisting}[language=bash]
$ ./harness_load_image \
    findings/load-image/default/crashes/\
    id:000000,sig:06,...,op:havoc,rep:2
\end{lstlisting}

\noindent ASan output (abridged):
\begin{lstlisting}
ERROR: AddressSanitizer: attempting free on
  address which was not malloc()-ed:
  0x507000000040 in thread T0
  #0 free (harness_load_image)
  #1 load_png  loader.c:633
  #2 load_with_builtin  loader.c:889
  #3 sixel_helper_load_image_file  loader.c:1418
  #4 sixel_encoder_encode  encoder.c:1743
  #5 main  harness_load_image.c:16
Alloc: malloc <- sixel_frame_new  frame.c:61
       <- load_with_builtin  loader.c:885
SUMMARY: bad-free in free
\end{lstlisting}

\subsection{Step 2 — Minimize with \texttt{afl-tmin}}

\begin{lstlisting}[language=bash]
$ afl-tmin \
    -i findings/load-image/default/crashes/\
       id:000000,sig:06,...,op:havoc,rep:2 \
    -o minimized_crash.png \
    -- ./harness_load_image @@
# File size reduced by: 86.67% (60 -> 8 bytes)
# 66 executions
\end{lstlisting}

The 8-byte minimized PoC is exactly the PNG magic bytes
(\texttt{89 50 4e 47 0d 0a 1a 0a}) with no IHDR or data chunks —
the shortest input that causes libpng to fail and trigger the
\texttt{longjmp} path leading to the bad free.

\subsection{Step 3 — Root Cause}

\textbf{Bug location:} \texttt{libsixel/src/loader.c:633} in \texttt{load\_png()}.

\textbf{Mechanism.}
\texttt{load\_png()} declares \texttt{unsigned char **rows} at line 315
\emph{without} the \texttt{volatile} qualifier and initialises it to \texttt{NULL}
at line 332 — \emph{after} the first \texttt{setjmp} call (line 323).
When libpng detects a malformed PNG (here: missing IHDR) it calls its
error callback, which executes \texttt{longjmp(png\_jmpbuf(png\_ptr), 1)}
— jumping back to the second \texttt{setjmp} at line 345.
Per C11~\S7.13.2.1, a non-\texttt{volatile} local whose value was changed between
the \texttt{setjmp} and the \texttt{longjmp} has \emph{indeterminate} value after
the jump; because \texttt{rows} was written \emph{after} the first \texttt{setjmp},
the compiler may keep it in a register that \texttt{longjmp} restores to a stale
value.
Execution falls through to the \texttt{cleanup} label, which calls
\texttt{sixel\_allocator\_free(allocator, rows)} (line 633) on that garbage pointer,
producing the \texttt{bad-free}.

\textbf{Bug classification.}
\begin{description}
  \item[ASan label] \texttt{bad-free} (free of non-malloc pointer)
  \item[CWE] CWE-825 — Expired Pointer Dereference (indeterminate pointer after
    \texttt{longjmp}); secondary CWE-755 (improper handling of exceptional conditions).
  \item[CVE] Matches the root cause of libsixel GitHub issue \#220~\cite{cve220}
    (\texttt{heap-buffer-overflow} in related PNG cleanup path, v1.8.6).
\end{description}

\section{Q6 — Attack Surface Analysis}
\label{sec:q6}
%-------------------------------------------------------------------------------

\subsection{Real-World Applications}

\textbf{Application 1: \texttt{img2sixel}.}
A command-line utility provided directly by the libsixel project.
It converts image formats such as PNG, JPEG, and BMP into SIXEL format so they can be
displayed inside a terminal emulator.
Any user who pipes or passes an untrusted image file to \texttt{img2sixel} triggers the
full image-loading and decoding pipeline in the process's security context.

\textbf{Application 2: FFmpeg-SIXEL.}
A collection of libraries and tools to process multimedia content (audio, video,
subtitles).
It enables, for instance, YouTube streaming rendered directly in the terminal.
Because FFmpeg fetches and decodes remote media, an attacker controlling a media stream
or file can deliver a crafted PNG that triggers the \texttt{bad-free} in
\texttt{load\_png} with no local file access required.

\subsection{Concrete Attack Scenario}

In an unsecured remote environment the \texttt{bad-free} vulnerability can lead to
arbitrary code execution.
An attacker crafts an image that forces \texttt{libsixel} to allocate memory in a
predictable pattern.
When the \texttt{bad-free} is triggered, the allocator metadata can be corrupted to
write attacker-controlled data into an arbitrary location — for instance, a function
pointer in a loaded library's GOT entry.
When the library subsequently calls through that pointer, execution is redirected to
attacker-supplied shellcode.
The attack requires no authentication and no interaction beyond delivering the
malicious image to a vulnerable application.

\subsection{Code Paths Not Exercised by the Harness}

\textbf{Gap 1: \texttt{sixel\_encode()} — raw encoder path.}
Our harnesses cover the decoder and the high-level image-loading encoder, but not the
raw pixel-buffer encoder (\texttt{src/tosixel.c}).
It processes dimensions and colour-reduction parameters that are partially
controlled by image metadata; integer overflow in dimension arithmetic could produce
an undersized output buffer.

\textbf{Gap 2: \texttt{sixel\_helper\_normalize\_pixelformat()} — pixel-format conversion.}
This function (\texttt{src/pixelformat.c}) performs arithmetic on width, height, and
bytes-per-pixel values derived from a decoded image.
Integer overflow in these calculations could produce an undersized destination buffer,
leading to an out-of-bounds write that our harness never reaches because we do not call
the pixel-format normaliser after decoding.

\section{Q7 — Binary-Only Fuzzing with QEMU Mode}
\label{sec:q7}
%-------------------------------------------------------------------------------

The vanilla binary was built with plain Clang (no AFL++ instrumentation, no ASan)
against a separately compiled \texttt{libsixel-vanilla} and launched under QEMU mode:

\subsection{Comparison: Instrumented vs.\ QEMU}

Both campaigns targeted \texttt{sixel\_decode\_raw} and ran for 40 minutes (2\,400\,s).
The instrumented baseline is \texttt{harness\_decode\_raw} (findings from
\texttt{findings/decode-raw}).

\begin{center}
\begin{tabular}{lcc}
\hline
\textbf{Metric} & \textbf{Instrumented} & \textbf{QEMU} \\
\hline
Duration             & 40 min & 40 min \\
Avg exec speed (exec/s) & 355 & 409 \\
Edges discovered     & 469 & 463 \\
Total edge map size  & 1\,065 & 65\,536 \\
Map density          & 44.04\% & 0.71\% \\
Corpus count         & 859 & 700 \\
Cycles done          & 2 & 3 \\
Saved crashes        & 0 & 0 \\
\hline
\end{tabular}
\end{center}

\textbf{Exec speed.}
QEMU mode ran at 409\,exec/s versus 355\,exec/s for the ASan-instrumented build —
a 15\% advantage.
This is counterintuitive: QEMU's JIT block translation adds overhead on first
execution, but for a short-running function like \texttt{sixel\_decode\_raw} the
translated blocks are cached and reused for every subsequent iteration.
The ASan runtime, by contrast, inserts a shadow-memory check before \emph{every}
load and store and runs heap quarantine logic on every allocation and free,
dominating per-execution cost.
Without ASan, compile-time instrumentation would be faster than QEMU; ASan inverts
the ordering here.

\textbf{Edges discovered.}
Both campaigns found almost identical code: 469 (instrumented) vs.\ 463 (QEMU).
The small gap reflects probabilistic hash collisions in QEMU's fixed 65\,536-slot
bitmap — two distinct edges that hash to the same slot are treated as one, slightly
undercounting unique paths.
The instrumented build assigns a unique ID to every CFG edge at compile time,
so all 469 are truly distinct.
The map-density figures (44\% vs.\ 0.71\%) are not comparable: the instrumented
build's denominator is the real number of edges in the binary (1\,065), while
QEMU's fixed 65\,536-slot map makes density a function of map size, not coverage.

\textbf{Corpus count.}
The instrumented campaign built a larger corpus (859 vs.\ 700) in the same time.
Collision-free edge IDs give AFL++ a more precise novelty signal: two inputs that
differ only in which of two colliding edges they hit are treated as distinct by
the instrumented build but identical by QEMU, so the instrumented fuzzer saves
more queue entries and explores a broader set of mutations.

\section{Q8 — Instrumentation Depth and Performance}
\label{sec:q8}
%-------------------------------------------------------------------------------

\subsection{Instrumented Edge Counts}

\begin{description}
  \item[\texttt{harness\_decode\_raw}] \textbf{1\,065} edges reported by AFL++ at
    startup (from \texttt{total\_edges} in \texttt{fuzzer\_stats}).
    This counts only edges reachable from \texttt{sixel\_decode\_raw} via the linker's
    dead-code elimination; the encoder, scaler, and pixel-format routines are stripped.
  \item[\texttt{harness\_decode}] \textbf{1\,057} edges — nearly identical, confirming
    both harnesses exercise the same decoder call graph.
  \item[\texttt{harness\_load\_image}] \textbf{16\,697} edges — significantly larger
    because \texttt{sixel\_encoder\_encode} pulls in the PNG/JPEG decoder chain
    (libpng, libjpeg), the colour-reduction path, and I/O wrappers.
\end{description}

The difference between the decode harness (1\,065 edges) and the image-loader harness
(16\,697 edges) illustrates how entry point selection determines instrumentation scope:
the same library produces very different coverage maps depending on which subsystem the
harness calls.

\subsection{Map Density vs.\ Total Edges}

The AFL++ status screen reports map density as $d = e_{\text{reached}} / e_{\text{total}}$.
Not all instrumented edges are reachable from \texttt{sixel\_decode\_raw}: encoder
paths, pixel-format converters, and write-side I/O routines are compiled in (if
\texttt{--whole-archive} is used) but never called by the harness.
Even among reachable edges, paths gated on rarely valid input sequences (e.g.,
a fully valid HLS colour triple followed by a specific run-length token) may
require many mutations to discover within 40 minutes.
In the QEMU campaign the reported density (0.72\%) is an artifact of the fixed
65\,536-slot map rather than a measure of real library coverage.

\subsection{Exec Speed Under Three Configurations}

\begin{center}
\begin{tabular}{lc}
\hline
\textbf{Configuration} & \textbf{Exec speed (exec/s)} \\
\hline
No sanitizer, fork mode   & 542 \\
ASan, fork mode          & 355 \\
ASan, persistent mode    & 23\,717 \\
\hline
\end{tabular}
\end{center}

\textbf{No sanitizer $\to$ ASan, fork mode slowdown (542 $\to$ 355\,exec/s).}
ASan inserts a shadow-memory check before every load and store, maintaining a
$1/8$-address-space shadow map.
This adds per-operation overhead and increases the process memory footprint,
making each fork slightly more expensive and reducing throughput by $\approx$35\%.

\textbf{Fork mode $\to$ persistent mode speedup (355 $\to$ 23\,717\,exec/s, $\approx$67$\times$).}
In fork mode, AFL++ forks a new process for every test case, paying the cost of
\texttt{fork(2)} and page-table copy-on-write on each execution.
Persistent mode keeps the process alive and loops inside \texttt{\_\_AFL\_LOOP(1000)},
amortising the fork cost over 1\,000 iterations.
For a lightweight, stateless function like \texttt{sixel\_decode\_raw} where process
startup dominates runtime, the speedup is at the high.
